# Constellations 运行诊断与 mo-linux 优化审查（2026-10-10）

本次先做只读审查；尚未改游戏、前缀或 profile。下面区分确认的错误、推断的原因和需要验证的修复。

## 1. ENB：已拿到准确编译错误（P0）

KiLoader 日志在前缀的 `drive_c/users/steamuser/AppData/Local/KiLoader/SkyrimSE/Logs/`，并不在普通 SKSE 日志目录。

10 月 9 日的 `KiENBExtender.log1.log` 记录：

```text
ENB Helper (1.4.3) loaded
Successfully initialized
External shader compilation failed:
E5020: The 'fx_5_0' target profile is only compatible with the 'fx' target type.
```

该编译错误重复 8 次。10 月 7、8 日的轮转日志也有同一错误。四个 Silent Horizons 2 shader 文件头是 `KIEFX`，并非 shader 缺失；KiLoader 和 Extender 初始化也成功。

有效配置 `enbseries/enbfxcompiler.ini` 是：

```ini
[EXTENDER]
EnableFileRelativeInclude = true
AllowMissingIncludeFiles = true
PreferNewestD3DCompiler = true
```

前缀 `system32/d3dcompiler_47.dll` 含 `Wine builtin DLL` 标记；游戏根的 `d3dcompiler_46e.dll` 来自 ENB Binaries v0505。

**强线索**：Extender 优先选择较新的 Wine 编译器，触发其 Effects profile 兼容性错误。当前证据尚不能代替实际模块加载追踪和修复后启动验证。

**建议的最小验证**：备份当前配置，通过独立的根目录修复 mod 覆盖 `enbseries/enbfxcompiler.ini`，将 `PreferNewestD3DCompiler` 改为 `false`，优先使用 ENB 随附的原生 46e；关闭游戏后部署，再检查新日志是否没有 E5020。若仍失败，追踪实际加载的编译器，再考虑原生 47，避免直接重装全部 ENB。

**mo-linux 改进**：`doctor` / `run --diagnose` 增加 KiLoader 日志读取与 `enb.compiler` 检查，识别 E5020、KIEFX 和加载失败；明确日志时间与轮转来源。`enb_binaries_present()` 目前只查 `d3d11.dll`，应同时检查所需 compiler，且不能将 DLL 存在等同于 ENB 可工作。

参考：[Extender 作者说明](https://www.nexusmods.com/skyrimspecialedition/mods/99406)（编译器选择与错误日志）、[WineHQ 同类 E5020 记录](https://list.winehq.org/mailman3/hyperkitty/list/wine-bugs%40winehq.org/message/3NNRCCEDKFHICFZZYAGHWGCZIHYODOQF/)。

## 2. 全部可选项被启用，产生相互覆盖（P0）

缓存的 rev 121 清单有 2444 项，其中 27 项 optional；profile 中这 27 项全部启用。作者缓存 README 明确写了不要全装，并要求可选项在基础配置工作后按需选择。

实际同时启用的不同玩法/显示方案包括：

- Story Mode 与 Hard Mode。
- Disable Survival Mode 与 Hardcore Survival。
- Full Restoration / Quest and Location Marker / Quest Marker 三个 Compass Restoration，以及 Hardcore Compass / Hardcore HUD。
- Performance 与 Ultra Performance ENB 补丁。
- 21:9 UI、手柄支持、ENB Frame Generation、Die When Killed（作者说明为永久死亡），均未经偏好筛选。

基础 ENB 预设与一个性能补丁可以叠加，但当前多个性能补丁同时启用，且有效 `enbseries.ini` 来自 Performance、`enbeffect.fx.ini` 来自 Ultra Performance，是混合方案。

**代码原因**：`InstallOptions::include_optional = true`；CLI 仅以 `--no-optional` 关闭。`collection.cpp` 的已安装快速路径还在 skip / optional 判断之前，旧实例重跑 `--no-optional` 不能可靠恢复为纯必需项。

**改进**：新实例默认 required-only，提供 `collection options` 预览、显式选择及可持久保存的 profile 方案；已有安装区分“磁盘上已装”与“当前 profile 启用”。保持旧实例迁移可预览，列出禁用结果，不静默改变已有存档的玩法。对互斥方案给出诊断；不能假设 Nexus 清单总会提供 conflicts 规则。

## 3. 用户描述的 roommap 加载错误：待原文确认（P0）

**后续更正**：用户明确症状是全局地图玩家当前位置显示 Unknown，而局部地图正常。确认已启用的 `Get Lost for Anniversary Edition`（Nexus mod 119736/file 513962）配置包含 `sCurrentLocationUnknownText = "Your current location is unknown."`；作者说明这就是隐藏玩家地图位置的设计。已通过 `mods disable` 停用、`apply` 部署，确认 farm 不再有 `GetLost.dll`。游戏内恢复情况待用户下次启动验证。以下是更正前的诊断状态。

尚未找到日志中叫 roommap 的模块。旧运行中的 FlatMapMarkersSSE、BakaWorldMapFilter、HDLocalMap、MapMarkerFramework 均有成功初始化记录；MapMarkerFramework 有无效 form 引用和可选 MergeMapper API 的警告，这些不能直接证明就是用户看到的弹窗。

需根据本次启动的英文弹窗和新日志定位；暂不据名字猜测停用地图 mod。

## 4. 诊断覆盖与配置校验（P1）

本次只读 doctor 返回 0 error、194 个 SKSE 插件 loaded，但 ENB 连续编译失败仍未报告。DLL 成功加载只说明初始化入口通过。

建议增加按插件分类的运行日志诊断，至少覆盖 KiLoader / ENB、明确的 JSON/TOML 解析失败及接口版本不匹配。区分必需功能失败、可选 API 缺失、历史日志，避免把所有 `error` 文本都当阻断项。

10 月 9 日日志还有 CraftingCategories 的 `NeaterCookingCategories.json` 解析错误和 SMP Wind 的 `Incompatible HDT-SMP interface`；需要各自按配置格式及接口版本继续验证，不能直接归因于 farm。

## 5. 存储与性能（P2）

- 下载缓存：`find_cached()` 每个 mod 重扫 downloads 并对同尺寸候选算 md5。建议一次构建大小索引，并缓存基于文件元信息的哈希；不能仅凭大小认定正确归档。用 2444 文件场景测量续装/verify 用时与 I/O。
- 游戏启动：先测 mod 扫描、farm diff、插件同步、SKSE 初始化、ENB 编译各段耗时，区分 mo-linux 用时和游戏自身用时。历史日志从插件初始化到 ENB 初始化约 4.5 分钟；不能承诺只优化 farm 就消除这段等待。
- 对解析 DLL 真实路径的插件，设计可选择的 reflink 部署模式；直接用硬链接会绕过现有基于 symlink 的 COW 保护，需同时验证 diff、写保护、overwrite capture，不能全局替换。
- ENB shader cache、GPU 选择与插帧选项应先在一致的预设下独立验证；配置混用时的性能结果不可作基准。

## 6. 文档一致性（P2）

HANDBOOK 中仍有“overwrite-root 不参与合并”“写穿未处理”和未验证游戏运行等早期段落，README / AGENT 的部分 Wabbajack 支持描述也需与当前实现核对。应标注当前能力、已验证范围与历史事故，避免指导后续 agent 做错误修复。

1. 收到本次弹窗原文，定位地图相关问题。

4. 补 doctor / diagnose 的回归测试：DLL 加载成功但 ENB 编译失败必须仍能报警；修复后不误报旧轮转日志。
5. 再测量并优化扫描、缓存及启动耗时。

## 追加：18:23:11 读旧存档崩溃

本次 CrashLogger 报 EXCEPTION_ACCESS_VIOLATION，首帧为 EngineFixes.dll 中 TBB 的 `MemoryPool::getTLS`，下一帧为 `scalable_malloc`。有效 EngineFixes 7.0 配置启用了内存管理替换，`bDisableTBB=false`。用户确认同一旧存档此前多次加载正常，本次疑似偶发。

目前只能确定崩溃地点在 allocator 内，不能证明 EngineFixes 是内存损坏的源头，更不能据栈上 Lux/NPC/地图对象直接停用它们。保留存档与当前 allocator 配置，复现时比较调用栈；若同类错误重复，再用可回滚 profile 对照测试 CRT allocator 或相应版本的内存管理开关，每次只改一个因素。上游 [issue #98](https://github.com/aers/EngineFixesSkyrim64/issues/98) 报告了临时 form 与内存管理的读档问题，但其签名与本次不完全相同，不能直接认定命中。
